# Internationalization (EN / FR)

**English** · [Français](../fr/i18n.md) — [← README](../../README.md)

DBDump ships in **English (primary) and French**. English is the source
language: it defines the shape of the dictionaries, occupies the root of the
site, and is the fallback everywhere else.

---

## Where the wording lives

| File                                    | Contents                                                     |
| --------------------------------------- | ------------------------------------------------------------ |
| `frontend/src/i18n/config.ts`           | List of locales, default locale, URL and tag helpers          |
| `frontend/src/i18n/dictionaries/en.ts`  | **All English wording** — the reference dictionary            |
| `frontend/src/i18n/dictionaries/fr.ts`  | French wording, typed `Dictionary`                            |
| `frontend/src/i18n/dictionary-types.ts` | Stable keys (features, steps, FAQ, platforms, formats)        |
| `frontend/src/i18n/provider.tsx`        | `I18nProvider` / `useI18n()`                                  |
| `frontend/src/i18n/locale-store.ts`     | Chosen language, persisted and shared between site and app    |
| `frontend/src/i18n/current.ts`          | Current language outside React (backends, Tauri calls)        |
| `frontend/src/i18n/format.ts`           | Numbers and file sizes through `Intl`                         |
| `frontend/src/i18n/metadata.ts`         | `<title>`, canonical URLs, `hreflang` alternates              |
| `desktop/src/i18n.rs`                   | Backend messages (`Lang`, `msg::*`)                           |

No user-facing string belongs anywhere else. A hardcoded string in a component
is a bug: it can only ever exist in one language.

---

## How a language is chosen

- **Landing page** — from the URL. `/` is English, `/fr/` is French. Each has its
  own root layout (route groups `(en)` and `(fr)`), so `<html lang>`, the
  canonical URL and the `hreflang` alternates are correct **in the served HTML**.
  There is no automatic redirect: the language switcher is a real link, and both
  pages are indexable.
- **App** (`/app/`) — at runtime, since a single HTML file is embedded by the
  desktop app: the language you picked (stored in `localStorage` under
  `dbdump.locale`), falling back to `navigator.languages`, then English. The
  switcher on the landing page writes to the same key, so a choice made on the
  site carries over into the app.

## Adding or changing a string

1. Add the key to `dictionaries/en.ts`, inside the section it belongs to
   (`landing`, `app`, `mock`, `demo`…).
2. Add the same key to `dictionaries/fr.ts`. **TypeScript enforces it**: `fr` is
   typed `Dictionary`, i.e. `typeof en` — a missing, renamed or wrongly-typed key
   fails the build.
3. Use it through the hook:

   ```tsx
   const { t } = useI18n();
   return <Button>{t.app.panel.run}</Button>;
   ```

Values with a placeholder are **functions**, not templates to concatenate — this
keeps word order free for each language:

```ts
// en.ts
latestVersion: (version: string) => `Latest version: ${version}`,
// fr.ts
latestVersion: (version: string) => `Dernière version : ${version}`,
```

Sentences that contain markup (a link, a `<code>`) are split into explicit
fragments (`…Before` / `…After`) rather than injecting HTML.

Outside React (mock backend, demo dump, Tauri calls), read the dictionary
through `currentDictionary()` — never cache it in a module-level constant, or a
language switch would not reach it.

## Backend messages (Rust)

The frontend passes its language to every command that produces user-facing
text:

```ts
invoke<BinaryStatus>("check_binary", { engine, lang: currentLocale() });
```

On the Rust side, `Lang` deserializes leniently (`fr-CA` → `Fr`, unknown → `En`)
and `msg::*` holds both variants side by side:

```rust
pub fn connection_established(lang: Lang) -> &'static str {
    lang.pick("Connection established", "Connexion établie")
}
```

**Not translated, on purpose:**

- the output of `pg_dump`, `mysqldump`, `mongodump`, `sqlite3` — relayed
  verbatim, because it is the exact cause of a failure and translating it would
  make it unsearchable;
- engine names (PostgreSQL, MySQL / MariaDB…) and command names, which are
  brands and identifiers;
- internal `store.rs` / `secrets.rs` errors, technical diagnostics kept in
  English.

## Adding a language

1. `frontend/src/i18n/config.ts`: add the code to `LOCALES`, plus its entries in
   `LOCALE_NAMES`, `LOCALE_SHORT` and `LOCALE_TAGS`.
2. Copy `dictionaries/en.ts` to `dictionaries/<code>.ts`, translate it, and type
   it `Dictionary`.
3. Register it in `dictionaries/index.ts`.
4. `frontend/src/i18n/metadata.ts`: add the OpenGraph locale.
5. Create the route: `src/app/(<code>)/layout.tsx` (root layout, `SiteHtml
   locale="<code>"`, `landingMetadata("<code>")`) and
   `src/app/(<code>)/<code>/page.tsx` on the model of `(fr)`.
6. `desktop/src/i18n.rs`: add the variant to `Lang`, extend `pick` and the
   `msg::*` functions.

The sitemap, the `hreflang` alternates and the language switcher are derived
from `LOCALES`: nothing else to wire up.

## Checks

```bash
npm --prefix frontend run build   # types + static export of every language
npm --prefix desktop run test     # cargo test, including Lang parsing
```

After a build, the served HTML can be checked directly:

```bash
grep -o '<html lang="[a-z]*"' frontend/out/index.html frontend/out/fr/index.html
```
