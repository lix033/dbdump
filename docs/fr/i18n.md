# Internationalisation (EN / FR)

[English](../en/i18n.md) · **Français** — [← README](../../README.fr.md)

DBDump est disponible en **anglais (langue principale) et français**. L'anglais
est la langue source : c'est lui qui décrit la forme des dictionnaires, qui
occupe la racine du site, et qui sert de repli partout ailleurs.

---

## Où vivent les textes

| Fichier                                 | Contenu                                                        |
| --------------------------------------- | -------------------------------------------------------------- |
| `frontend/src/i18n/config.ts`           | Liste des langues, langue par défaut, helpers d'URL et de tags   |
| `frontend/src/i18n/dictionaries/en.ts`  | **Tous les textes anglais** — dictionnaire de référence          |
| `frontend/src/i18n/dictionaries/fr.ts`  | Textes français, typés `Dictionary`                              |
| `frontend/src/i18n/dictionary-types.ts` | Clés stables (features, étapes, FAQ, plateformes, formats)       |
| `frontend/src/i18n/provider.tsx`        | `I18nProvider` / `useI18n()`                                     |
| `frontend/src/i18n/locale-store.ts`     | Langue choisie, persistée et partagée entre le site et l'app      |
| `frontend/src/i18n/current.ts`          | Langue courante hors React (backends, appels Tauri)              |
| `frontend/src/i18n/format.ts`           | Nombres et tailles de fichiers via `Intl`                        |
| `frontend/src/i18n/metadata.ts`         | `<title>`, URL canoniques, alternates `hreflang`                 |
| `desktop/src/i18n.rs`                   | Messages du backend (`Lang`, `msg::*`)                           |

Aucune chaîne visible par l'utilisateur ne doit vivre ailleurs. Une chaîne en dur
dans un composant est un bug : elle n'existera jamais que dans une seule langue.

---

## Comment la langue est choisie

- **Landing** — par l'URL. `/` est en anglais, `/fr/` en français. Chacune a sa
  propre racine (route groups `(en)` et `(fr)`), donc `<html lang>`, l'URL
  canonique et les alternates `hreflang` sont corrects **dans le HTML servi**.
  Aucune redirection automatique : le sélecteur de langue est un vrai lien, et
  les deux pages sont indexables.
- **App** (`/app/`) — à l'exécution, puisqu'un seul fichier HTML est embarqué par
  le desktop : la langue choisie (mémorisée dans `localStorage`, clé
  `dbdump.locale`), sinon `navigator.languages`, sinon l'anglais. Le sélecteur de
  la landing écrit dans la même clé : un choix fait sur le site suit dans l'app.

## Ajouter ou modifier un texte

1. Ajoutez la clé dans `dictionaries/en.ts`, dans la section qui convient
   (`landing`, `app`, `mock`, `demo`…).
2. Ajoutez la même clé dans `dictionaries/fr.ts`. **TypeScript l'impose** : `fr`
   est typé `Dictionary`, c'est-à-dire `typeof en` — une clé oubliée, renommée ou
   mal typée casse la compilation.
3. Utilisez-la via le hook :

   ```tsx
   const { t } = useI18n();
   return <Button>{t.app.panel.run}</Button>;
   ```

Les valeurs à trou sont des **fonctions**, pas des gabarits à concaténer — cela
laisse l'ordre des mots libre dans chaque langue :

```ts
// en.ts
latestVersion: (version: string) => `Latest version: ${version}`,
// fr.ts
latestVersion: (version: string) => `Dernière version : ${version}`,
```

Les phrases contenant du balisage (un lien, un `<code>`) sont découpées en
fragments explicites (`…Before` / `…After`) plutôt que d'injecter du HTML.

Hors React (backend simulé, dump de démo, appels Tauri), lisez le dictionnaire
via `currentDictionary()` — ne le mémorisez jamais dans une constante de module,
un changement de langue ne l'atteindrait pas.

## Messages du backend (Rust)

Le frontend transmet sa langue à chaque commande qui produit du texte lu par
l'utilisateur :

```ts
invoke<BinaryStatus>("check_binary", { engine, lang: currentLocale() });
```

Côté Rust, `Lang` se désérialise avec tolérance (`fr-CA` → `Fr`, inconnue →
`En`) et `msg::*` garde les deux variantes côte à côte :

```rust
pub fn connection_established(lang: Lang) -> &'static str {
    lang.pick("Connection established", "Connexion établie")
}
```

**Volontairement non traduits :**

- la sortie de `pg_dump`, `mysqldump`, `mongodump`, `sqlite3` — relayée telle
  quelle, parce que c'est la cause exacte d'un échec et que la traduire la
  rendrait introuvable ;
- les noms de moteurs (PostgreSQL, MySQL / MariaDB…) et de commandes, qui sont
  des marques et des identifiants ;
- les erreurs internes de `store.rs` / `secrets.rs`, diagnostics techniques
  laissés en anglais.

## Ajouter une langue

1. `frontend/src/i18n/config.ts` : ajoutez le code à `LOCALES`, ainsi que ses
   entrées dans `LOCALE_NAMES`, `LOCALE_SHORT` et `LOCALE_TAGS`.
2. Copiez `dictionaries/en.ts` vers `dictionaries/<code>.ts`, traduisez, et typez
   le tout `Dictionary`.
3. Déclarez-le dans `dictionaries/index.ts`.
4. `frontend/src/i18n/metadata.ts` : ajoutez la locale OpenGraph.
5. Créez la route : `src/app/(<code>)/layout.tsx` (racine, `SiteHtml
   locale="<code>"`, `landingMetadata("<code>")`) et
   `src/app/(<code>)/<code>/page.tsx`, sur le modèle de `(fr)`.
6. `desktop/src/i18n.rs` : ajoutez la variante à `Lang`, complétez `pick` et les
   fonctions `msg::*`.

Le sitemap, les alternates `hreflang` et le sélecteur de langue se déduisent de
`LOCALES` : rien d'autre à brancher.

## Vérifications

```bash
npm --prefix frontend run build   # types + export statique de toutes les langues
npm --prefix desktop run test     # cargo test, dont l'analyse de Lang
```

Après un build, on peut contrôler directement le HTML servi :

```bash
grep -o '<html lang="[a-z]*"' frontend/out/index.html frontend/out/fr/index.html
```
